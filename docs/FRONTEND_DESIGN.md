# Figure Alert — 앱 화면 설계

2026-10-13. 사용자 위임에 따른 디자인 설계. 실제 앱 구현·API 연결·사용성 검증 완료를 뜻하지 않는다. Android/iOS와 구현 프레임워크는 아직 미정이다. 기존 Java/Spring 백엔드를 유지하고 화면이 백엔드 계약에 맞게 연결되도록 설계한다.

## 목적과 참고 기준

‘관심 캐릭터의 소식을 놓치지 않기’를 중심으로 읽기 쉬운 일정·명확한 출처·간단한 구독 설정을 제공한다. 화려한 상품 쇼핑 화면보다 소식 확인과 다음 행동을 앞에 둔다.

참고: [Apple 탭 바 지침](https://developer.apple.com/design/human-interface-guidelines/tab-bars), [Apple 알림 지침](https://developer.apple.com/design/human-interface-guidelines/notifications/), [Material 색상 역할](https://m3.material.io/styles/color/roles), [Material 글자 체계](https://m3.material.io/styles/typography/applying-type). 고정된 주요 탐색 위치와 역할별 색상·읽기 쉬운 글자 구분을 참고했다. 아래 색상·화면 구성은 이 서비스에 맞춘 설계 판단이다.

## 시각 방향

차분한 밝은 배경에 깊은 청록을 강조색으로 사용한다. 캐릭터 팬 서비스의 분위기를 살리면서도 상품 이미지와 일정 정보가 묻히지 않도록 장식은 줄인다. 청록은 제품 브랜드색이며 특정 캐릭터만 지원한다는 의미가 아니다.

| 역할 | 색상 | 용도 |
|---|---|---|
| 배경 | #F5F7F8 | 전체 화면 |
| 표면 | #FFFFFF | 카드·설정 영역 |
| 주요 글자 | #172B35 | 제목·본문 |
| 보조 글자 | #52636D | 출처·설명 |
| 강조 | #006B63 | 저장 버튼·선택 탭·켜진 스위치 |
| 강조 표면 | #E4F4F1 | 관심 캐릭터·선택 배경 |
| 긴급 글자 / 배경 | #9A3412 / #FFF1E8 | 공식 예약 마감 임박 |
| 오류 | #B42318 | 실패 안내 |
| 구분선 | #DCE3E7 | 카드·행 경계 |

마감은 색만으로 표현하지 않고 ‘예약 마감 임박’과 공식 날짜를 함께 표시한다. 켜짐·꺼짐도 화면 읽기 도구가 상태를 알 수 있게 한다. 일반 본문 대비 4.5:1을 목표로 실제 조합을 검증한다. 본문 기본 크기 16, 보조 14, 화면 제목 24~28을 기준으로 시스템 글자 확대를 지원한다. 터치 영역은 iOS 44pt·Android 48dp 이상을 설계 목표로 삼고 실제 플랫폼에서 확인한다. 간격은 8 단위, 화면 좌우 여백 20, 카드 모서리 16을 기본으로 한다. 고정 높이로 글자를 자르지 않는다.

## 메뉴와 핵심 화면

하단 메뉴: 소식 / 탐색 / 내 구독 / 내 정보. 메뉴는 로그인 여부에 따라 사라지지 않는다. 개인 기능 선택 시 로그인으로 연결하고 원래 목적 화면으로 복귀한다. 검색·공개 상품 조회는 로그인 없이 사용할 수 있게 한다. 관리자 기능은 소비자용 하단 메뉴에 넣지 않는다.

| 코드 | 화면 | 구성과 이유 | 백엔드 상태 |
|---|---|---|---|
| NTF-01 | 소식 | 내 관심 소식, 읽지 않음 표시, 상품·캐릭터·이벤트 종류·공식 날짜·출처. 로그인 후 기본 목적 화면 | Notification·이벤트 API 미구현 |
| CAT-01 | 탐색 | 검색과 캐릭터 필터, 결과 카드. 마케팅 배너 대신 찾기 기능 우선 | Figure 조회 코드 존재, 계약 확인 필요 |
| CAT-02 | 상품 상세 | 상품 정보, 예약·발매·재발매 이력, 적용 공식몰·출처, 캐릭터 구독 진입 | 예약·출처 데이터는 추가 설계 필요 |
| SUB-00 | 내 구독 | 캐릭터별 수신 상태, 모두 끔 상태 명시, 설정 진입 | 목록 조회 API 미구현 |
| SUB-01 | 캐릭터 구독 설정 | 캐릭터명, 다섯 설정 행, 상태 안내, 저장 버튼 | PUT 계약 기획 완료, 구현 전 |
| ACC-01 | 내 정보 | 계정·로그아웃·향후 기기 알림 설정 | 회원·JWT 코드 존재, 자동 갱신 미구현 |

상품 이미지 사용권이 확인되지 않으면 텍스트와 중립 플레이스홀더로 구성한다. 공식 이미지를 임의로 복제하지 않는다. 실제 데이터 없는 화면에서 허위 소식·가입자 수를 표시하지 않는다.

## SUB-01 상세 구성

위에서 아래로: 뒤로 가기 + ‘알림 설정’ → 캐릭터명과 구독 상태 → ‘받고 싶은 소식을 선택하세요’ → 다섯 스위치 → 상태 안내 → 저장 버튼. 하단 저장 영역은 안전 영역을 고려하고 글자 확대 시 내용 스크롤을 가리지 않는다. 구독 취소는 저장과 구분하되 취소 기능 계약은 별도 작업이다.

| 표시명 | 입력 필드 | 설명 |
|---|---|---|
| 신규 피규어 발표 | announcementEnabled | 공식 신규 발표가 확인되면 안내 |
| 예약 시작 | preorderEnabled | 공식 예약 시작이 확인되면 안내 |
| 예약 마감 임박 | deadlineEnabled | 확인된 공식 마감 3일 전 안내; 마감 변경 안내 포함 |
| 재발매 | rereleaseEnabled | 기존 상품의 공식 재발매 소식 |
| 프라이즈 등장 예정 | prizeEnabled | 공식 등장 예정 정보 확인 시 안내 |

모든 필드를 Boolean으로 전달한다. 현재 인증 회원 ID를 요청 본문에 넣지 않는다. PUT /characters/{characterId}/subscription을 사용하고 신규 201·갱신 200 모두 같은 성공 흐름으로 표시한다. 응답의 구독 ID·캐릭터 ID·다섯 설정으로 저장 결과를 갱신한다. 백엔드 내부 클래스를 화면 상태 구조로 그대로 복제하지 않는다.

신규 화면은 모두 끄고 시작하며 진입만으로 저장하지 않는다. 신규 구독은 모두 끈 상태라도 저장할 수 있어야 한다. 기존 구독은 저장값을 불러오며, 조회 실패 시 모두 끔으로 대체하지 않는다. 기존 설정 조회 API는 PUT 외에 필요한 계약으로 아직 구현되지 않았다.

## 확정된 상태별 동작

| 상태 | 화면 | 서버와의 관계 |
|---|---|---|
| 저장 중 | 저장 버튼·다섯 스위치 잠금, 진행 표시. 앱 내 이동을 제한하고 안내 | 요청 한 번 전송; 서버 중복 방지 별도 유지 |
| 성공 | 현재 화면 유지, 응답 설정 반영, 모든 잠금 해제, ‘저장했습니다’ | 커밋 성공 후의 응답만 성공으로 표시 |
| 모두 끔 저장 성공 | ‘관심 캐릭터로 저장했습니다. 현재 모든 알림이 꺼져 있습니다.’ 및 ‘구독 중 · 알림 꺼짐’ | 추가 확인창 없음 |
| 캐릭터 없음 | 확정 안내 표시, 입력 유지, 목록으로 돌아갈 수 있게 함 | 404, 저장 없음 |
| 재로그인 필요 | 같은 계정이면 입력 복원 후 확인·저장; 다른 계정은 이전 입력 미적용 | 재로그인 후 자동 저장 안 함 |
| 응답 확인 불가 | 원인을 단정하지 않는 안내·입력 유지·잠금 해제·재시도 | UX 설명안은 검토 중; 무조건 저장 실패로 단정하지 않음 |
| 미저장 변경 후 나가기 | ‘계속 수정’ / ‘저장하지 않고 나가기’ | 후자는 저장 요청 없음 |

미저장 상태는 마지막 확인된 서버 설정 또는 신규 화면의 초기 선택과 현재 선택을 비교한다. 값이 같아지면 변경 없음으로 본다. 단, 신규 화면에서 저장하지 않고 나가면 구독은 생성되지 않는다. 응답 확인 불가 때 서버 저장 여부와 화면의 미저장 표시를 혼동하지 않도록 별도 상태로 둔다. 앱 강제 종료까지 차단하지 않는다.

## 핵심 서비스와 현재 개발 범위의 차이

사용자가 앱을 열지 않아도 소식을 받으려면 기기 푸시 등 외부 전달이 필요하다. ‘앱으로 만들기’만으로 사이트 내 알림이 푸시로 바뀌지는 않는다. 푸시 권한·토큰·발송은 이후 알림 기획에서 별도 결정한다. 사용자가 미루기로 한 알림 중복 방지 상세 논의는 여기서 확정하지 않는다.

이번 구현은 SUB-01의 설정 저장을 중심으로 한다. 소식·내 구독 목록·푸시 화면은 전체 앱 설계에 포함하지만 동작 완료라고 주장하지 않는다. 네이티브/크로스플랫폼 기술 선택은 대상 OS와 개발 역량을 확인한 뒤 비교한다.

## 검증과 인수인계

백엔드 검증은 SUBSCRIPTION_PUT_PLAN.md를 따른다. 프런트엔드는 글자 확대·작은 화면·화면 읽기·색 대비, 신규/기존 설정 로드, 전체 false, 성공 응답, 실패·시간 초과, 저장 중 조작과 이동, 미저장 확인, 계정 변경 후 입력 미적용을 검증한다. mock 성공은 실제 API 연동 성공과 구분한다.

성과 검증: 사용자가 설명 없이 원하는 종류를 선택해 저장할 수 있는지, 모두 끔 상태에서 알림이 오지 않음을 이해하는지, 실패 뒤 다음 행동을 찾을 수 있는지 관찰한다. 저장 완료 시간·완료율·오해 사례를 기록하고 측정 전 개선 수치를 만들지 않는다.
