# 캐릭터 구독 PUT — 변경 범위와 검증 기준

2026-10-13 작성. 구현 계획이며 기능 변경·테스트 실행 완료를 뜻하지 않는다. 정책 근거는 PROJECT_PLAN.md의 확정 정책 1~5다.

## 사용자에게 제공할 결과

한 번의 설정 저장으로 캐릭터 구독을 생성하거나 변경한다. 같은 설정을 반복 저장해도 구독이 늘어나지 않는다. 모든 알림을 꺼도 관심 캐릭터는 유지한다. 동시 생성 충돌은 서버가 처리하며 실제 저장 실패는 성공으로 안내하지 않는다.

## 현재 코드에서 확인한 차이

- CharacterSubscription: 회원·캐릭터 UNIQUE와 createdAt은 존재. 알림 설정은 없음.
- CharacterSubscriptionService.subscribe: 기존 구독이면 예외. 설정 갱신·충돌 재처리 없음.
- Repository: 회원·캐릭터 조회는 존재하므로 재사용 가능.
- JWT 필터: 인증 principal에 Long 회원 ID를 저장. 요청 본문에서 회원 ID를 받을 필요 없음.
- SecurityConfig: POST/DELETE의 복수형 subscriptions 경로만 USER로 지정. 새 PUT 단수형 subscription 경로의 명시적 권한 규칙 필요.
- 구독 Controller/DTO 없음. 제조사 서비스 Mockito 테스트는 있으나 실제 DB 구독 경쟁 테스트는 확인되지 않음.

## 함께 확정한 범위와 입력 계약

사용자 확정: 이번 구현 범위는 구독 생성·설정 변경·전체 알림 끄기·동시 요청 처리까지다. 실제 알림 생성은 다음 작업으로 둔다.

사용자 확정: 입력 방식은 A안(다섯 설정을 항상 모두 전달해 전체 교체)이다. 누락·null은 입력 오류이며 false는 정상 값이다. 일부 값만 전달해 나머지를 유지하는 B안보다 화면에서 선택한 전체 상태와 저장 결과가 명확하고 검증하기 쉬워 선택했다. 아래 계약 중 응답 형식 등 나머지 내용은 함께 검토할 초안이다.

사용자 확정: 저장 후 응답은 B안(실제 저장된 설정도 반환)이다. 구독 ID·캐릭터 ID·저장된 다섯 알림 설정을 반환해 화면을 해당 요청의 저장 결과로 갱신한다. 성공 여부만 반환하는 방식보다 추가 조회 없이 결과를 확인할 수 있어 선택했다. 이 응답은 이후 다른 요청에 의한 변경까지 막거나 최신 상태를 영구 보장하지 않는다. 생성 시각의 응답 포함 여부는 아직 확정하지 않았다.

사용자 확정: 성공 응답은 신규 생성 201, 기존 설정 갱신 200으로 구분한다. 동시 생성 충돌 후 기존 구독을 갱신하면 200이다. 구독 소유자는 서버가 검증한 인증 정보의 회원 ID로 결정하고, 요청 본문에는 회원 ID를 받지 않는다.

사용자 확정: 대상 캐릭터가 존재하지 않으면 구독을 저장하지 않고 ‘해당 캐릭터를 찾을 수 없어 구독을 저장하지 못했습니다. 캐릭터 목록에서 다시 확인해 주세요.’로 안내한다. 입력한 설정은 화면에 유지한다. 검증 기준은 없는 캐릭터 요청에 404 응답·구독 생성 또는 변경 없음·안내 표시·입력값 유지다. 화면 관련 기준은 화면 구현 시 검증하며 백엔드 테스트 완료와 구분한다.

## API 계약 — 함께 확정한 항목 외에는 초안

사용자 확정: 인증 문제로 저장이 중단되고 같은 계정으로 재로그인하면 입력한 설정을 복원하되 자동 저장하지 않는다. 사용자가 설정을 확인하고 저장 버튼을 다시 누른다. 재로그인으로 흐름이 끊긴 뒤 예전 선택을 자동 적용하는 것보다 사용자 의도를 다시 확인할 수 있어 선택했다. 다른 계정으로 로그인하면 이전 계정의 입력을 적용하지 않는다. 검증 기준은 같은 계정의 입력 복원·저장 전 DB 변경 없음·확인 후 저장, 다른 계정의 입력 미적용이다.

인증 유지 방향은 유효기간이 있는 액세스 토큰과 리프레시 토큰으로 자동 갱신하는 안을 설명한 상태다. 구체적인 수명·보관·교체·철회와 구현 범위는 아직 확정하지 않았다. 재로그인 후 확인 저장 결정과 자동 갱신 기능 구현 완료를 구분한다.

PUT /characters/{characterId}/subscription

인증된 USER의 principal을 회원 ID로 사용한다. 경로 ID는 양수이며 실제 캐릭터가 존재해야 한다.

본문: announcementEnabled, preorderEnabled, deadlineEnabled, rereleaseEnabled, prizeEnabled 다섯 Boolean을 모두 필수로 받는다. false는 허용하며 누락·null은 400으로 거부한다. 전체 교체 의미를 유지하기 위해 누락을 기존 값 유지나 false로 추정하지 않는다.

응답: 실제 신규 생성은 201, 기존 설정 갱신과 생성 충돌 후 갱신은 200. 구독 ID·캐릭터 ID·저장된 다섯 설정·생성 시각을 DTO로 반환한다. 엔티티 자체를 응답하지 않는다. 신규 응답의 Location은 해당 구독 경로를 사용한다.

없는 캐릭터는 404. 인증 없음·유효하지 않은 인증은 401, USER 권한 없음은 403을 목표로 하되 현재 Security 설정이 이를 반환하는지 먼저 검증한다. 저장·재처리가 실패하면 적절한 5xx로 응답하고 내부 DB 정보는 노출하지 않는다.

## 저장 중 화면 동작 — 확정

사용자 확정: 저장 중 앱 내 뒤로 가기와 화면 이동을 잠깐 막고 ‘저장 중입니다. 잠시만 기다려 주세요.’라고 안내한다. 성공·실패·응답 대기 시간 초과 시 이동 제한을 해제한다. 화면 이동이 이미 전송한 요청을 취소하는 것으로 오해하지 않게 하기 위해 선택했다. 운영체제의 앱 강제 종료·중단까지 막을 수 있다고 가정하지 않는다. 검증 기준은 앱 내 이동 차단·안내와 모든 종료 경로의 제한 해제다. 사용자가 프런트엔드 화면 구성·색상 설계를 위임했으며 FRONTEND_DESIGN.md에서 백엔드 계약과 연결한다.

사용자 확정: 다섯 알림이 모두 false인 상태로 저장에 성공하면 ‘관심 캐릭터로 저장했습니다. 현재 모든 알림이 꺼져 있습니다.’라고 안내하고 화면에 ‘구독 중 · 알림 꺼짐’을 표시한다. 별도의 확인창은 띄우지 않는다. 알림 없는 구독을 허용하면서도 구독만으로 알림이 올 것이라는 오해를 줄이기 위해 선택했다. 일반 성공 문구 대신 이 문구를 신규 생성과 기존 설정 갱신 모두에 적용한다. 검증 기준은 전체 false 저장 성공 시 해당 문구와 상태 표시, 추가 확인창 없음, 현재 화면 유지다.

사용자 확정: 새 캐릭터 구독 화면의 초기 알림 선택은 다섯 종류 모두 false다. 모든 알림을 자동 선택하는 방식보다 사용자가 받을 소식을 직접 고르게 하기 위해 선택했다. 화면 진입만으로 구독을 생성하지 않으며 저장을 눌렀을 때 생성한다. 모두 false로 저장해도 구독은 유지하는 기존 확정 정책을 따른다. 기존 구독은 저장된 다섯 설정을 그대로 표시하며 초기값으로 덮어쓰지 않는다. 검증 기준은 신규 화면에서 다섯 스위치 꺼짐, 진입만으로 저장 요청 없음, 전체 false 저장 성공·구독 생성, 기존 구독 설정 보존이다. 기존 데이터의 DB 초기값 정책은 신규 화면 기본값 결정과 별개로 확인한다.

사용자 확정: 설정을 변경한 뒤 저장하지 않고 화면을 나가려 할 때만 ‘저장하지 않은 변경 사항이 있습니다.’ 확인창을 표시한다. 선택지는 ‘계속 수정’과 ‘저장하지 않고 나가기’다. 전자는 화면과 입력을 유지하고, 후자는 변경을 버리고 이동하며 저장 요청을 보내지 않는다. 현재 선택과 마지막으로 확인한 서버 설정을 비교하며, 변경을 되돌려 동일해졌거나 저장 성공 후에는 확인창 없이 이동한다. 실수로 입력을 잃는 것을 막되 변경 없는 이동은 방해하지 않기 위해 선택했다. 검증 기준은 미저장 변경 시 확인창 표시, 계속 수정 시 입력 유지, 버리고 나가기 시 저장 요청 없음, 변경 없음·원상 복구·저장 성공 후 확인창 없음이다. 새 구독의 초기 선택값, 저장 중 이동, 결과 확인 불가 이후 이동, 앱 강제 종료 시 복원 여부는 별도 미결정 사항이다.

사용자 확정: 저장 성공 후 이전 화면으로 자동 이동하지 않고 현재 구독 설정 화면을 유지한다. 서버 응답의 저장된 설정을 표시하고 ‘저장했습니다’라고 안내한다. 사용자가 저장 결과를 즉시 확인하고 필요하면 수정할 수 있어 선택했다. 검증 기준은 성공 후 자동 이동 없음, 실제 응답 설정 표시, 성공 안내, 저장 버튼·다섯 스위치 잠금 해제다.

사용자 확정: 저장 처리 중에는 저장 버튼뿐 아니라 알림 선택 스위치 다섯 개도 비활성화한다. 요청을 보낸 후 화면의 선택만 변경되어 저장 결과와 달라지는 상황을 방지하고, 현재 표시된 설정이 저장 대상임을 명확히 하기 위해 선택했다. 성공·실패·응답 대기 시간 초과 시 저장 버튼과 스위치 잠금을 함께 해제한다. 성공 시 해당 요청에서 실제 저장된 설정을 표시하며, 실패·시간 초과 시에는 사용자의 입력을 유지한다. 검증 기준은 처리 중 스위치 조작으로 값이 바뀌지 않음, 모든 종료 경로의 잠금 해제, 성공 시 응답 설정 표시, 실패·시간 초과 시 입력 유지다. 알림 생성의 중복 방지 상세 논의는 사용자 요청에 따라 이후 알림 구현 단계로 미룬다.

사용자 확정: 저장 요청 처리 중에는 저장 버튼을 비활성화하고 ‘저장 중…’을 표시한다. 중복 클릭을 허용하는 방식보다 진행 상태를 명확하게 보여주고 불필요한 요청을 줄일 수 있어 선택했다. 성공·실패·응답 대기 시간 초과 시 다시 조작할 수 있게 한다. 대기 시간이 초과되면 ‘저장 결과를 확인하지 못했습니다’로 안내하며 저장 실패를 단정하지 않는다. 입력을 유지하고 다시 시도할 수 있게 한다. 대기 시간 수치는 아직 정하지 않았다. 버튼 잠금은 다른 기기·네트워크 재시도를 막지 않으므로 서버의 멱등성·동시성 처리를 유지한다. 검증 기준은 처리 중 중복 클릭의 추가 요청 없음, 진행 표시, 성공·실패·시간 초과 뒤 잠금 해제, 시간 초과 시 입력 유지와 결과 불확실 안내다.

## 파일별 변경 범위

사용자 확정 — 기존 구독 설정 변경: 개별 setter를 다섯 번 호출하는 대신 다섯 boolean을 모두 받는 changeSettings 메서드로 전체 교체한다. 회원·캐릭터·ID·createdAt은 변경하지 않는다. 생성자·메서드 선언·호출의 인자 순서는 신규 발표, 예약 시작, 예약 마감, 재발매, 프라이즈로 통일한다. Java는 인자 위치로 연결하고 모두 같은 타입이므로 순서 오류를 컴파일로 발견할 수 없다는 한계가 있다. 호출 인자를 한 줄씩 표시하고 각 설정만 켜는 테스트로 연결 오류를 검증한다. 메서드 호출 자체와 DB 트랜잭션의 원자성은 별개이며 Service 설계에서 연결한다. 실제 구현은 파일을 확인한 뒤 진행한다.

사용자 확정 — Entity 타입과 생성: 알림 다섯 필드는 boolean과 @Column(nullable = false)로 표현한다. DTO의 Boolean은 누락 검사용이며 Entity는 켜짐·꺼짐만 저장한다. 신규 생성자는 Member·Character와 다섯 설정을 모두 받는다. 생성 후 별도로 설정하는 방식보다 설정 호출을 잊어 기본 false가 저장되는 위험을 줄이기 위해 선택했다. 기존 두 인자 생성자를 제거하고 호출부를 새 생성자에 맞춘다. JPA용 protected 기본 생성자는 유지한다. 인자가 길고 같은 boolean 타입이라 순서 혼동이 가능하다는 단점은 받아들이되 각 필드 연결과 혼합 값 저장을 검증한다. 설정 전체 false도 정상 생성되어야 한다. 실제 DB NOT NULL 적용과 기존 행의 초기값은 별도 확인한다. 기능 코드 변경·테스트는 아직 미완료다.

| config/SecurityConfig.java | PUT 경로 USER 권한과 인증 실패 응답 검증·필요 수정 |
| exception/GlobalExceptionHandler.java | 새 API의 입력 오류·최종 실패 응답이 일관적인지 확인 후 필요한 부분만 수정 |
| 테스트·build.gradle | 서비스·HTTP 계약 검증과 실제 MySQL 경쟁 테스트에 필요한 최소 구성 |

경로는 src/main/java/com/figure/figure 기준. 기존 중복 구독 예외는 참조를 확인한 후 불필요하면 정리한다. 기존 데이터가 있다면 다섯 설정의 초기값과 DB 변경 절차를 먼저 정한다. 알림 도입 전 데이터라는 이유만으로 기존 사용자에게 모두 수신을 자동 설정하지 않는다.

## 충돌 재처리 설계

새 트랜잭션에서 조회→생성 또는 전체 갱신→flush→커밋한다. 커밋까지 완료된 뒤 성공을 반환한다. 트랜잭션 밖에서 같은 회원·캐릭터 UNIQUE 제약의 생성 충돌만 판별하고, 새 트랜잭션에서 기존 행을 조회·갱신하는 재처리를 한 번 수행한다.

모든 DataIntegrityViolationException을 중복 구독으로 취급하지 않는다. 실패한 트랜잭션 안에서 다시 저장하지 않는다. 같은 클래스 내부 호출의 @Transactional에 의존하지 않는다. TransactionTemplate으로 경계를 명시하는 방식을 우선 검토하면 재시도만을 위한 Service 추가를 피할 수 있다. 제약 식별은 실제 MySQL 예외로 검증한다. 재처리 시 행이 없거나 다시 실패하면 성공으로 처리하지 않는다.

설정은 한 트랜잭션에서 다섯 필드를 전부 교체한다. 서로 다른 동시 요청은 DB에서 나중에 반영된 설정이 남는다. 클릭 순서 보장은 하지 않는다. 무제한 재시도는 하지 않는다.

요청 식별자와 작업 결과(생성·갱신·충돌·재처리 성공·최종 실패)를 연결해 기록한다. JWT·비밀번호·요청 전체를 로그에 남기지 않는다. 저장 성공 로그는 커밋 이후 기록한다.

## 검증 완료 기준

사용자 확정 — 잘못된 자료형: 알림 설정은 JSON boolean만 허용하고 문자열·숫자 등을 추측 변환해 저장하지 않는다. HTTP 400으로 요청 전체를 거부하고 기존 설정을 유지한다. @NotNull은 변환 후 null 여부만 검사하므로 JSON 역직렬화 단계의 변환 허용 설정과 별개다. 실제 프로젝트의 JSON 변환기·설정과 다른 API 영향을 확인한 뒤 최소 변경으로 구현한다. 테스트에는 문자열 false·끄기, 숫자 0/1 등 비 boolean 입력 거부를 포함한다. 이 경우의 오류 코드 통합 여부와 전역 변환 정책 변경은 아직 확정하지 않았다.

사용자 추가 확정 — 누락 상세와 화면 안내 분리: 여러 항목의 누락·null은 모두 개발자용 상세 메시지에 포함한다. 순서는 다섯 설정의 화면 표시 순서로 고정한다. 앱은 INVALID_SUBSCRIPTION_SETTINGS 응답의 상세 메시지를 사용자에게 그대로 표시하지 않고 ‘설정을 저장하지 못했습니다. 문제가 계속되면 문의해 주세요.’로 안내하며 입력을 유지한다. 정상 앱이 항상 다섯 항목을 보내야 하므로 사용자가 누락을 직접 수정하도록 요구하지 않는다. 일부 값만 온 요청은 전체 거부하며 신규 생성·기존 설정 변경 모두 수행하지 않는다. 개발 기록에는 필요한 오류 코드와 누락 필드명만 남기고 인증 토큰·요청 전체를 기록하지 않는다. 기존의 ‘대상 설정 안내’ 검증은 개발자용 응답 상세 검증을 뜻하며 사용자 화면의 일반 안내와 구분한다. 추가 검증: 복수 누락의 상세 포함, 앱의 일반 안내와 입력 유지. 구현·테스트는 아직 미수행이다.

2026-10-16 사용자 확정 — 요청 설정 검증: 다섯 필드는 Boolean으로 받고 @NotNull과 요청 본문의 @Valid 검증을 연결한다. 하나라도 누락·null이면 Service 호출 전에 전체 요청을 거부하고 기존 데이터는 유지한다. true·false 및 전체 false는 허용한다. 잘못된 요청으로 저장 로직과 불필요한 DB 작업을 실행하지 않는 것이 목적이다.

2026-10-16 사용자 확정 — 오류 응답: 상태·메시지만 제공하는 방식보다 식별 가능한 고정 오류 코드가 필요해 status·code·message 방식으로 확장한다. 설정 누락·null은 INVALID_SUBSCRIPTION_SETTINGS 하나로 묶고 메시지로 대상 설정을 설명한다. 필드별 코드를 만들지 않아 코드 관리 부담을 줄인다. 문구가 바뀌어도 오류 종류를 구분할 수 있지만 코드 의미·일관성을 관리해야 한다. 오류 코드는 분류이며 실제 원인 추적 로그를 대체하지 않는다. HTTP 상태와 status는 400으로 일치시킨다. 여러 설정이 동시에 빠졌을 때 메시지의 표현 방식은 아직 미결정이다.

현재 ErrorResponse는 status·message만 가지므로 code 추가 시 기존 생성자·예외 처리·응답 소비자의 영향을 확인한다. 이 결정은 모든 기존 오류의 코드를 일괄 확정하거나 기능 구현을 완료했다는 뜻이 아니다. 검증 기준: 각 필드 누락·명시적 null에서 HTTP 400 및 해당 code, 대상 설정 안내, Service 호출 없음; 기존 설정 보존은 DB 통합 검증으로 별도 확인. 정상 true/false 조합·전체 false는 검증을 통과해야 한다. 모두 아직 미실행이다.

| 상황 | 확인할 결과 | 검증 수준 |
|---|---|---|
| 처음 저장 | 201, 구독 하나, 다섯 설정 일치 | HTTP + DB |
| 기존 설정 변경 | 200, 같은 ID·createdAt, 다섯 설정 전체 교체 | 서비스 + DB |
| 동일 요청 반복 | 구독 하나, 같은 최종 설정 | HTTP + DB |
| 모두 false | 저장 성공, 구독 유지 | 서비스 + HTTP |
| 값 누락·null / 잘못된 ID | 400, 저장 없음 | HTTP |
| 없는 캐릭터 | 404, 저장 없음 | 서비스 + HTTP |
| 인증·권한 오류 | 401/403, 타인 구독 변경 불가 | Security 통합 |
| 동일 설정 동시 생성 | 두 요청 처리 완료, 행 하나, 설정 일치 | 독립 연결·트랜잭션의 실제 MySQL |
| 다른 설정 경쟁 | 행 하나, 어느 한 요청의 전체 설정, 혼합 없음 | 실제 MySQL |
| 다른 DB 제약·연결 오류 | 충돌 재처리로 숨기지 않음, 실패 응답 | 오류 주입 + 가능 범위의 DB 검증 |
| 재처리 실패 | 제한된 시도 후 실패, 성공 응답 없음, 연결된 로그 | 서비스 + 트랜잭션 검증 |

Mockito만으로 UNIQUE 경쟁·rollback·커밋을 검증했다고 주장하지 않는다. 경쟁 테스트는 두 요청이 모두 생성 경로에 진입하도록 동기화하고, 대기 시간 제한을 둔다. 한 외부 테스트 트랜잭션에 모두 묶지 않는다. 운영 DB에 테스트하지 않는다. 실제 DB 환경이 없으면 미검증으로 명시한다.

## 이번 작업과 이후 알림 작업의 연결

이번 완료 범위는 설정 저장·권한·동시성이다. 현재 Notification·이벤트·공식 예약 마감 데이터가 없어 ‘구독 직후 마감 안내’까지 구현 완료라고 표시할 수 없다. 그것은 다음 알림 작업의 별도 수용 기준으로 유지한다. 외부 호출을 구독 저장 트랜잭션에 추가하지 않는다.

구현 전 추가 확인: 기존 구독 데이터의 기본 설정, 마감 알림 재활성화 정책, DB 변경 방식, 실제 테스트 환경. 신규·반복 PUT 구분과 마감 안내 이벤트 중복 방지는 이후 알림 작업에서 함께 검증한다.

성과 설명: 중복 요청에서 사용자가 재시도해야 하는 A안보다 서버가 충돌을 처리하는 B안을 선택했다. 검증 후 실제 경쟁 요청 수·저장 행 수·최종 실패 수를 기록한다. 운영상 구독 완료율 개선은 배포 후 측정하며 지금 수치로 주장하지 않는다.
