## 확인과 판단

- Entity·Controller·Service·Repository·JWT/Security·요청/오류 DTO·테스트·빌드 설정 확인.
- 카탈로그·회원/JWT 코드 있음. 구독은 다섯 설정·생성·갱신 Service까지 있으나 Controller·응답·조회·취소·경쟁 재처리 없음.
- 캐릭터 POST가 ADMIN 제한 없이 인증만 요구하고, 공개 캐릭터 GET도 인증을 요구하는 규칙 불일치 발견. 실행 재현은 아직 아님.
- 내부 알림·이벤트·스케줄러·푸시·토큰 갱신·클라이언트·배포 구성은 미구현/미확인.
- 구독 오류 코드는 기획에만 있고 기존 handler는 첫 검증 메시지만 반환. Figure 삭제의 Release FK 충돌 가능성과 생성 입력 검증 차이 확인.
- 대안: 새 기능부터 늘리기 / 기존 핵심 흐름을 검증하고 연결하기. 후자를 추천. 사용자에게 새 기능을 보여주는 시점은 늦지만 기반 오류와 권한 문제를 조기에 찾을 수 있음.
- 순서 제안: 실행 기반·필수 권한 → 구독 완성 → 이벤트/내부 알림 → 배포 필수 보완·클라이언트 → 사용자 피드백·포트폴리오.

## 다음 작업

### 후속 실습 기록

- 후속 확인: 사용자가 기존 구독 갱신 테스트를 복원하고 신규 생성 테스트와 함께 실행해 두 개 모두 통과했다고 보고했다. 테스트 파일의 두 메서드 존재 확인. 가짜 Repository 기반의 생성/갱신·설정 전달·반환 결과·신규 save 호출 검증이며 실제 DB 저장·커밋·경쟁 요청 검증은 아니다. 다음은 없는 회원·캐릭터에서 저장을 막는 실패 테스트다.

- 사용자 보고: Entity의 예약 시작만 켜기, 기존 구독 Service 갱신, 신규 구독 Service 생성 테스트 각각 실행 성공. Mockito의 동적 Agent 경고는 테스트 실패와 분리하고 명시적 Agent 설정을 후속으로 남김.
- 최신 Service 테스트 파일 리뷰: 신규 생성 테스트의 회원·캐릭터·설정·created=true·save 호출 검사를 확인했다. 현재 파일에는 신규 생성 메서드만 있고 이전 갱신 메서드는 없어 회귀 검증 복원 필요. 과거 사용자 보고와 현재 파일의 검사 범위를 구분한다. AI는 이번 테스트를 재실행하지 않음.

- 사용자가 CharacterSubscriptionTest를 직접 작성했다. 모두 true인 객체 준비 → changeSettings에 모두 false 전달 → 다섯 getter를 assertFalse로 검사하는 코드 확인.
- 사용자 보고: IntelliJ에서 해당 테스트 실행 성공. AI가 이번 테스트를 별도로 재실행하거나 IDE 결과를 직접 확인한 것은 아님. 검증 범위는 Java 객체의 전체 알림 끄기이며 DB 반영·권한·동시성은 제외.
- 실행 중 공유된 JPA Dialect 오류는 Tomcat·restartedMain 로그가 있어 테스트 대신 앱 실행 가능성을 안내했다. DB 오류 원인은 확정하거나 수정하지 않았다. 이후 사용자가 테스트 성공을 보고함.
- 다음 검증 제안: 특정 알림만 켜기. 모두 동일한 false 입력만으로는 인자 순서·필드 연결 오류를 발견하기 어려우므로 혼합 값으로 검사한다. 아직 작성·실행하지 않음.

- 빌드·기존 테스트는 통과했으므로 구독 생성·갱신·전체 false·없는 회원/캐릭터 테스트부터 이어간다. 실제 변경 감지는 DB 통합 테스트로 별도 검증한다.
- 기획 초안과 사용자 확정을 구분하며 전체 구현을 한 번에 대행하지 않는다.
