# 2026-10-16 일일 스크럼·작업 결과

## 목표와 실제 결정

- 목표: 구독 PUT 입력 누락의 처리와 오류 응답 기준을 함께 정리.
- 사용자 판단: 불완전한 요청은 저장 메서드 호출 전에 막는다. 메모리 절약보다 잘못된 저장 실행 방지가 주된 목적임을 확인.
- 입력 기준: Boolean + @NotNull, 요청 본문 @Valid. true·false 허용, 누락·null은 거부.
- 비교: 상태·메시지만 반환 / 필드별 오류 추가 / 고정 오류 코드 추가.
- 사용자 선택: status·code·message. 누락·null은 INVALID_SUBSCRIPTION_SETTINGS 하나로 묶고 메시지로 설정을 설명.
- 이유: 문구와 무관하게 오류 종류 식별. 단점은 코드 정의·일관성 관리 필요. 오류 코드는 원인 추적 로그를 대신하지 않음.
- 학습: Controller·Service 모두 서버에서 실행. 입력 범위 검사와 DB 존재 확인을 구분. false와 누락의 차이를 확인.

## 근거와 검증

- ErrorResponse 코드 확인: status·message만 있어 code 추가 시 기존 예외 처리 영향 확인 필요.
- 변경: 구독 계획과 진행 현황, 오늘 기록. 기능 코드 변경 없음.
- 검증 계획: 누락·null의 400/code/메시지, Service 미호출, 기존 DB 설정 보존, 정상 조합 통과.
- 빌드·테스트·DB 검증: 미실행. 사용자 성과·성능 개선 수치 없음. 작업시간·비용 미기록.
- 역할: 사용자가 처리·응답 방식을 선택하고 AI는 비교·개념 설명·문서화를 지원.

## 다음 작은 결정

- 코드 확인: 사용자가 Entity에 다섯 boolean 필드·NOT NULL 매핑·전체 인자 생성자·changeSettings를 추가한 것을 확인했다. 아직 테스트하지 않았으며 Service는 기존 두 인자 생성자 호출 상태라 연계 수정이 필요하다. 다음은 요청 DTO를 받아 생성·갱신에 전달하는 Service 변경 안내다.

- 사용자 확정: 기존 구독은 changeSettings로 다섯 설정을 전체 교체. 생성자와 동일한 인자 순서 사용. 같은 타입 인자 순서 오류는 컴파일로 잡히지 않아 각 필드 단독 활성화 테스트로 검증한다. 다음은 Service의 기존 구독 조회 이후 생성·갱신 분기를 연결한다.

- Entity 설계 사용자 확정: 다섯 boolean 필드와 DB NOT NULL 매핑. 새 생성자는 회원·캐릭터·다섯 설정을 모두 받는다. 설정을 나중에 넣는 호출을 잊을 위험을 피하기 위한 선택이다. 기존 두 인자 생성자 호출부 수정, JPA 기본 생성자 유지, boolean 인자 순서 혼동 검증이 필요하다. 해당 Entity 코드는 아직 변경하지 않았다.

- 후속 사용자 확정: 문자열·숫자 등 잘못된 설정 자료형은 자동 해석하지 않고 요청 거부. DTO의 null 검증과 JSON 변환 단계 검증을 구분하고 실제 변환기 동작을 테스트해야 한다. 아직 기능 코드는 수정하지 않았다.
