# Figure MVP 코드 점검과 완성 순서

기준일: 2026-10-20. 소프티어 9기 준비를 위한 개인 프로젝트 진행 기준. 모집 일정·평가 기준을 조사한 문서가 아니며 합격 가능성을 보장하지 않는다. 현재 체크아웃의 소스를 직접 확인했다. 기존 사용자 수정과 미추적 문서를 유지하며 기능 코드는 이번 점검에서 변경하지 않았다.

## 목표와 범위

사용자가 관심 캐릭터를 구독하고 검증된 공식 소식을 내부 알림에서 확인할 수 있는 첫 버전을 완성한다. 카탈로그 조회·회원/인증·캐릭터 구독·내부 알림 V1은 기존 합의한 첫 배포 범위다. 단순히 API 개수를 늘리기보다 한 사용자 흐름을 실제 DB·권한·오류와 함께 설명하고 재현할 수 있어야 한다.

개별 피규어 구독·위시리스트·리뷰·가격 비교·대규모 성능 최적화는 후속이다. 앱 푸시와 토큰 자동 갱신은 미구현이며, 배포 전 제공 경험과 인증 정책을 별도 결정한다. 내부 알림을 푸시처럼 표현하지 않는다. 이번 문서는 우선순위 제안이며 미결정 정책을 자동 확정하지 않는다.

## 현재 구현 현황

| 기능 | 코드에서 확인한 내용 | 아직 완료가 아닌 이유 |
|---|---|---|
| 피규어 | 등록·목록·상세·수정·삭제, 이름/캐릭터 검색·제조사 필터 | API·DB·권한 통합 검증 없음. 발매 이력이 있는 상품 삭제 정책 확인 필요 |
| 캐릭터 | 등록·목록·상세·검색·캐릭터별 피규어 조회 | 공개 조회 정책과 현재 인증 규칙 불일치. 등록 ADMIN 제한 누락 |
| 제조사 | 등록·목록·변경·삭제, 이름 중복 검사·연결 상품 삭제 방지 | 동시 중복·실제 FK 검증 없음. 단위 테스트 1개만 존재 |
| Release | 최초/재발매/재입고, 상태, 연·월·일 기반 일정·가격·일정 변경 | 예약 시작·마감·공식 출처·확인 시각·프라이즈 일정 데이터 없음 |
| 회원·인증 | 가입·BCrypt 검증·JWT 발급·인증 필터 | 잘못된/만료 토큰·401/403·동시 가입·입력 길이 검증 필요. 자동 갱신 없음 |
| 캐릭터 구독 | 다섯 설정 DTO·Entity·생성자·changeSettings·회원/캐릭터 UNIQUE·Service 생성/갱신 | Controller·응답 DTO·조회·취소 없음. 경쟁 생성 재처리 없음 |
| 오류 응답 | status·message, 일부 404/409/400 매핑 | code 없음. 검증 오류는 첫 항목만 반환. 구독 자료형 엄격 검증 미연결 |
| 내부 알림 | 기본 정책 문서 있음 | 이벤트·Notification·생성·목록·읽음·스케줄러 코드 없음 |
| 앱·배포 | 화면 설계 초안 | 클라이언트 구현·배포 설정·일반 사용자 이용 흐름 없음 |

기존 등록·관리 API는 초기 데이터 운영에 재사용한다. 공개 제조사 API·자동 수집·검색 결과 자동 발송을 가정하지 않는다.

## 발견한 우선 수정 사항

1. **권한 불일치:** CharacterController의 POST /characters에 ADMIN 규칙이 없고 anyRequest().authenticated()에 걸린다. 현재 규칙상 인증된 일반 USER도 등록 가능한 구조다. GET /characters 계열도 공개 규칙이 없어 비로그인 탐색이 차단되는 구조다. 실제 응답은 Security 통합 테스트로 재현해야 한다.
2. **구독 API 연결 누락:** SecurityConfig에는 POST/DELETE 복수형 subscriptions만 있고, 실제로 계획한 PUT 단수형 subscription Controller는 없다. Service 존재만으로 사용자 기능이 완성되지 않는다.
3. **구독 동시성:** find 후 없으면 save하는 구조는 경쟁 생성에서 UNIQUE 예외를 낼 수 있다. 매핑은 있지만 현재 충돌 식별·새 트랜잭션 재처리는 없다. 실제 MySQL 경쟁 테스트가 필요하다.
4. **검증 계약 불일치:** DTO에 @NotNull은 있지만 호출할 Controller가 없다. 오류 code·복수 누락·엄격한 JSON boolean 변환 거부도 아직 없다.
5. **삭제 정합성 위험:** FigureService.deleteFigure는 FigureCharacter만 삭제한다. 연결 Release가 있는 경우 삭제가 FK에 막힐 수 있다. 삭제 거부/연관 데이터 처리 정책을 함께 결정하고 500 대신 명확한 응답을 검증한다. 실제 오류는 아직 재현하지 않았다.
6. **생성 입력의 불일치:** FigureUpdateRequest와 달리 생성 요청에는 캐릭터 ID 중복·양수·길이 검증이 부족하다. 중복 ID가 없는 캐릭터로 잘못 분류될 수 있어 생성/수정 기준을 비교한다. 회원 길이 제한도 DB 한도와 대조한다.

## 실행 순서와 완료 기준 — 제안

### P0: 재현 가능한 개발·테스트 기반

문제: 현재까지 코드 존재와 테스트 성공을 구분할 근거가 부족하다.

- Java 21과 wrapper로 빌드·기존 테스트 확인. 실행 환경과 실패 원인 기록.
- 기존 운영 데이터에 접속하지 않는 별도 테스트 DB/프로필 마련. ddl-auto=update를 데이터 변경 계획으로 대체했다고 간주하지 않음.
- 비로그인·USER·ADMIN 경로별 권한 표 작성 및 캐릭터 등록/공개 조회 규칙 보완.
- 완료 기준: 빌드·기존 테스트 결과 재현, 테스트 격리, USER의 관리 API 거부와 공개 조회·401/403 검증.

### P1: 캐릭터 구독을 실제 사용자 기능으로 완성

이미 작성한 코드를 버리지 않고 이어간다.

1. 생성·changeSettings·Service 정상 분기의 작은 테스트를 먼저 마련.
2. 저장 결과 응답 DTO와 PUT Controller 연결. 인증 principal에서 회원 ID 사용, 신규 201·갱신 200.
3. Boolean 누락/null·잘못된 자료형·잘못된 경로 ID·없는 캐릭터·오류 code·복수 상세를 연결.
4. 현재 구독 설정 조회와 구독 취소를 작은 기능으로 구현. 조회 시 구독 없음 표현, 취소의 반복 호출 결과는 함께 결정한다. 알림 모두 끔과 구독 취소는 구분.
5. 기존 데이터의 초기 설정·DB 제약 적용 확인. 같은 회원/캐릭터 충돌만 제한적으로 재처리하고 결과 기록.

완료 기준: 새 구독·전체 교체·모두 끔·반복 PUT·다른 회원 격리·입력 실패 시 DB 불변·읽기·취소 검증. 실제 MySQL 독립 트랜잭션 경쟁에서 행 하나와 정의한 응답 보장. mock 테스트로 커밋·정합성 검증을 대체하지 않음.

### P2: 공식 이벤트에서 내부 알림까지 연결

작은 완성 단위로 ‘검증된 신규 발표 1건 → 해당 종류 구독자에게 알림 → 본인 목록 조회 → 읽음 처리’를 먼저 구현한다. 과거 카탈로그 등록을 신규 발표로 취급하지 않는다. 해당 흐름 검증 후 예약 시작·재발매·프라이즈·예약 마감으로 확장한다. 기능 확장은 순서 차이이며 기존 알림 5종 정책을 삭제하거나 첫 범위에서 임의 제외하는 결정이 아니다.

- 공식 출처·확인 시각·이벤트 식별·상품/Release 연결부터 최소 설계.
- 다중 캐릭터 관계·반복 실행에서도 회원/이벤트 중복 방지, 본인 알림 권한 검증.
- 확정한 구독 이후 적용·전체 끔·신규 구독 마감 임박 예외·마감 변경 안내를 각각 테스트.
- 날짜 정밀도·시간대·일정 변경 식별·재활성화 등 아직 미결정 정책은 해당 구현 직전에 함께 결정.
- 완료 기준: 이벤트 등록부터 조회·읽음까지 DB 기반 재현, 과거 상품 무알림, 다른 회원 읽음 변경 차단, 재실행 중복 없음, 마감 변경·알 수 없는 날짜 정책 확인.

### P3: 카탈로그·인증의 배포 필수 보완과 이용 가능한 배포

권한과 데이터 손실 위험은 P0/P1에서도 발견 즉시 해결한다. 이 단계는 기존 기능을 모두 다시 만드는 작업이 아니다.

- 검색·수정·삭제 FK, 잘못된 날짜·길이·중복 ID·가입 중복의 정상/실패 응답 검증.
- 목록 데이터 상한·페이지 정책을 실제 초기 데이터 규모에 맞춰 결정. 근거 없는 인덱스·캐시 도입 금지.
- 런타임 설정·비밀값 분리·DB 변경 절차·로그·백업/복구·기본 배포 상태 확인을 필요한 범위로 정리.
- API 서버 배포와 일반 사용자의 이용 가능 상태를 구분. 앱/최소 클라이언트 제공 방식 결정 후 핵심 흐름 연결.
- 완료 기준: 새 환경 실행 절차 재현, 가입→로그인→탐색→구독→알림 확인을 직접 이용 가능. 실패·권한·재시작 후 데이터 보존 확인.

### P4: 사용자 검증과 포트폴리오 증거 정리

- 실제 테스트 사용자에게 핵심 과제를 수행하게 하고 어려움·오해·반복 사용을 기록. 아직 사용자 수 목표 달성 주장은 없음.
- README에 실행·구현 범위·핵심 흐름·ERD·API 계약·결정 이유·실제 테스트 결과·남은 한계 연결.
- 트러블슈팅은 재현한 문제만, 성능은 측정값만 기록. 채용 목표 때문에 수치나 협업 경험을 만들지 않음.
- 완료 기준: 한 기능의 문제→대안→선택→검증→한계를 본인이 코드와 증거로 설명 가능. 무작위 코드 설명과 보안·무결성 전체 검토를 함께 수행.

## 당장 다음 작업

빌드·기존 테스트 결과 확인 후 구독 Entity·Service의 생성/갱신/전체 false/잘못된 대상 테스트를 작은 단위로 진행한다. 이후 구독 Controller·응답 DTO를 연결한다. 완성 코드 전체를 AI가 일괄 작성하지 않고 기존 학습 방식대로 대상 파일·이유·검증을 안내한다. 테스트 의존성·격리 방식은 실제 빌드와 환경을 보고 최소 구성으로 정한다.

기간과 마감일은 미정이다. 소프티어 준비의 실제 제출/지원 일정과 투입 가능 시간을 확인하기 전 완료 날짜를 약속하지 않는다.

## 실행 검증 기록

- JDK: 로컬 Temurin 21.0.12.1 경로 확인. 기본 PATH에는 Java가 없어 실행 시 JAVA_HOME을 지정.
- Gradle: wrapper 9.5.1, Spring Boot 선언 4.1.1. 버전 표기와 빌드 성공은 별개.
- 기존 자동 테스트: 제조사 중복 등록 방지 단위 테스트 1개 확인. 구독·Security·DB 통합 테스트 파일 없음.
- 실행: JAVA_HOME을 JDK 21로 지정하고 프로젝트 .gradle/audit-user-home 캐시에서 gradlew.bat test --no-daemon 수행. 최초 DNS 실패 후 승인된 네트워크 실행으로 재시도.
- 결과: BUILD SUCCESSFUL, compileJava·compileTestJava·test 완료. 기존 제조사 중복 이름 테스트 1개 통과. 보고서: ../build/reports/tests/test/index.html, XML: ../build/test-results/test/TEST-com.figure.figure.service.ManufacturerServiceTest.xml.
- 해석: 현재 코드의 컴파일과 해당 단위 테스트는 검증됨. 실제 DB 연결·트랜잭션·권한·구독 저장·서버 실행·배포는 아직 미검증. 프레임워크 버전을 임의 변경하지 않았다.
